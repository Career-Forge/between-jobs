# Hiring Signals golden input: `search_hits.json`

Real search-index results for `site:linkedin.com/posts` hiring queries, sanitized.
Per [../../README.md](../../README.md) rule 1 these come from real runs, not from
imagination; rule 2 is what the rest of this file is about.

## Provenance

- Captured 2026-09-19 through the Firecrawl **search** endpoint only. No
  scrape, crawl, map, extract or fetch call was made, and no `linkedin.com` URL was
  requested by any means -- the feature this fixture serves never fetches
  LinkedIn, and neither did its capture.
- 24 queries (two returned nothing), more than 200 results in all. The queries have
  the shape the P2 query builder produces: hiring vocabulary OR'd, role terms OR'd,
  a metro (tab surface) or a company (per-JD surface), and a freshness window
  (`qdr:d` / `qdr:w` / `qdr:m`, or none). They cover India-style and global
  vocabulary, several role families (software, product, sales, HR/finance,
  engineering, healthcare, pharma, marine), non-English vocabulary (es, pt, fr, de,
  zh, ja, hi, ar), plus three probes: `inurl:ugcPost`, a query without the `/posts/`
  scope, and a bare `feed/update` query (which returned nothing).
- 84 rows were selected from that capture so that every species and every
  title/url/snippet shape the parser has to handle is present. The raw capture stays
  outside the repository (it contains real names).
- 14 more rows (three `second_capture_*` pulls) were added later, the same day, from
  a review pass over the parser: 28 queries generated by the P2 query builder itself
  and a few probes for localized auto-generated posts. They are the real cases the
  first 84 did not contain -- dated drives with the day cut off by the snippet
  ellipsis, an auto-generated post cut before its closing sentence, its German,
  French and Portuguese twins, pipe titles with a tagline or a company name that
  contains a pipe, a post whose url names no author, and a real hiring post that
  says "open to work". Search-result fields only (url, title, snippet); no page was
  fetched. Twelve are organization pages posting as themselves; two were
  person-authored (a recruiter's hiring post, and a walk-in post under a
  person-style handle) and were sanitized like the first 84.
- Provider field mapping: Firecrawl's `description` is stored as `snippet`;
  `position` is dropped. Each `hits` entry is `{url, title, snippet}`, the shape the
  P3 provider adapters map into.

## Layout

`pulls[]`, one per query (or per group of rows from the same query family), each
with `pull_id`, `locale` (`india` / `global` / `non_english`), `kind` (`tab` /
`per_jd` / `probe`), `freshness_window`, a plain-words `query_shape`, and `hits[]`.
A pull is the unit the aggregator check runs over, so pulls were kept whole where
that matters (`aggregator_template_blr`, `sales_mumbai`).

There is no `expected/` directory on purpose. Snapshotting the parser's output
would only prove the parser agrees with itself; `tests/test_hiring_signals.py`
instead asserts explicit values that were decided by reading the sanitized records.

## Sanitization applied

Consistent replacement, so parsing paths still exercise the same shapes:

- **Person names** (post authors and people named inside snippets) became synthetic
  names, replaced identically in the title, the url handle/slug and the snippet.
  Case, script and shape were preserved: `'s Post` vs `' Post` possessives, ALL-CAPS
  and lower-case surnames, names with parentheses/commas/periods, an accented Latin
  name (percent-encoded in its handle), and a Latin+CJK name.
- **Profile handles** with a person-style suffix (`-4823463a7`, `-882520349`,
  `...999`) became synthetic handles with the same suffix shape. Company-page vanity
  handles are public and were kept.
- **Activity / ugcPost ids**: random digits of the same length (19), the same real id
  mapped to the same synthetic id everywhere (two real posts share one id under two
  slugs, and one real post appears in two pulls with different snippets). The 4-character
  url suffix was re-randomized position by position, keeping the `-` / `_` characters
  where they occurred. Because the ids are synthetic, the `posted_at` the parser
  decodes from a fixture id is meaningless (some decode to a future year); tests
  never assert it on fixture rows. The id-to-time decoding itself was checked
  against the real ids of the raw captures, where all 320 posts that carried a
  provider age stamp agreed with it.
- **Tracking token**: the one `rcm=` member token in a real url is the placeholder
  `ACoAAEXAMPLE0000000000000000000000000`.
- **Links**: every `http(s)` link inside a title or snippet (`lnkd.in`, `bit.ly`, a
  YouTube link, a personal project site) became `https://example.com/l/<hash>` (same
  real link, same placeholder); bare domains became `example.com` / `jobs.example.com`.
- **Emails** became `careers@example.com`. There were no phone numbers or WhatsApp
  links in the selected rows.
- **Instagram shortcodes** (two rows kept as non-LinkedIn-host examples) are random.
- Personal text that identifies a private individual was rewritten by hand, not
  just re-named: the five job-seeker / referral / layoff rows (two job seekers' own
  pleas, a nurse's job search, a layoff-related offer to refer, a layoff-advice post)
  got a hand-written snippet that keeps the words the classifier keys on ("can refer
  me", "I'm looking for my next role", "I'm happy to refer you") and nothing else,
  and their url slugs and one title -- which were the post's own hashtags and
  headline -- were replaced with generic ones. Commenter and profile headlines that
  sat verbatim next to synthetic names (`... @ Example Institute` and four
  others: a mentor tagline, an infrastructure-engineer headline, a finance headline,
  a college name) were generalized to a bare role.
- **Kept**: company names, company pages and their handles, role text, locations,
  salary text, and one public job id -- company and role facts are what the ATS-echo
  matching tests need. `HireHub.io` is a company page name, not a domain to hide.
- **Everything else is verbatim public text.** Company and page names, role and
  location text, hashtags, recruiter copy and search-snippet wording are as the index
  returned them; the sanitization replaces identities, links and identifiers, not
  prose. A snippet of a company's own hiring post can therefore be found by searching
  its words, which is fine for an organization advertising a job and is the reason the
  personal-text rows above were rewritten instead of only renamed.

```
grep -o '[A-Za-z0-9._+-]*@[A-Za-z0-9. -]\{0,20\}' search_hits.json | sort | uniq -c
    -> careers@example.com (x2), "@ Example Institute" (x1)
grep -c 'linkedin.com/in/' search_hits.json                                  -> 0
grep -ciE 'wa\.me|bit\.ly|lnkd\.in|t\.me/|whatsapp' search_hits.json         -> 0
grep -oE 'https?://[^/" ]+' search_hits.json | sort | uniq -c
    -> www./es./pt./fr./de./cn./uk.linkedin.com, example.com, www.instagram.com (x2)
```

plus a scripted pass over every title and snippet for non-LinkedIn bare domains
(only `example.com` variants and `HireHub.io`) and for digit runs of 7 or more
(`20.09.2026`, a date, and `200040449`, a public job id -- no phone numbers), and a
by-eye read of all 98 records. The scripts that build and edit the fixture assert
that no replaced real name, handle or id survives anywhere in the output, and a
scratch-only denylist of every real name and handle seen in any capture was grepped
across this fixture, this README, the parser module and the test file (the denylist
itself is personal data and is not in the repository).
`test_fixture_contains_no_contact_details_or_profile_urls` and
`test_fixture_http_hosts_are_linkedin_instagram_or_example_dot_com` keep the committed
fixture from regressing, and
`test_no_contact_details_or_real_profile_links_in_anything_this_feature_commits` applies
the structural checks (email domains, profile links, tracking tokens, phone-shaped
numbers) to this README, the parser module and the test file too -- a docstring
example is read by strangers as much as a fixture row is.

## Composition

98 rows, 97 distinct urls, 19 pulls (locale: 48 india, 30 global, 20 non-English;
surface: 85 tab, 8 per-JD, 5 probe).

Parsed species (91 rows): `unclassified` 56, `ats_echo` 15, `hiring_drive` 10,
`referral_offer` 7, `job_seeker` 3. Rejected (7 rows): `unsupported_urn` 3 (`ugcPost`),
`not_linkedin` 2 (Instagram), `not_a_post_url` 2 (`/jobs/view/`). `unclassified` is the
default species -- most real hiring posts land there, and so do event invites and
welcome posts; it claims nothing.

Title shapes (the first 84 rows; the later 14 add a lone bare `<Company>`, a pipe
title with a tagline after the name, a content-only pipe title, a pipe inside the
company name, and two `<Company> - <localized verb> #hiring` titles):
`<X>'s Post [- topic]` 26, `<content> | <X>` 12, `<X> - <topic>` 8,
`<X> posted this / on the topic / ...` 6, `#hiring | <Company>` 6, content-only
truncated 6, content-only 5, localized prefix (`Publicación de`, `Post de`,
`Beitrag von`, `Publicação de`) 5, `<Company> - hiring` 3, `... | <X> | N comments` 3,
`<X>' Post` 2, `<X>的动态` 1, leading-pipe 1. Across all 98, 77 titles carry
` - LinkedIn`, 19 have no site suffix, 10 end in an ellipsis.

URL shapes: 2 with no slug (`_activity-`), 1 with no author handle at all
(`/posts/activity-<id>-<suffix>`), 13 with the bare `hiring` slug plus 2 with a localized
one (`embauchons-hiring`, `contratando-hiring`), 11 percent-encoded, 3 LinkedIn urls
with a trailing slash, 1 with a tracking query string, 6 whose suffix starts or ends
with `-`/`_`, hosts `www.` (83), `pt.` (3), `es.`/`fr.`/`de.`/`cn.`/`uk.` (2 each).

Snippet shapes: 69 lead with `N days ago ·`, 5 with `N hours ago ·`, 24 with no stamp
(mostly non-English and month-window results), 80 end in an ellipsis.

## What this fixture does not cover

Represented once or not at all -- tests for these use minimal **synthetic** strings,
labeled as such in the test names:

- `1 hour ago` / `Just now` / `N minutes|weeks|months ago` stamps (the provider
  only ever produced `hours` and `days` in this capture; a `qdr:h` query returned
  nothing).
- `de.linkedin.com`, the leading-pipe title, the `<X>的动态` title and the
  tracking-query url each appear once.
- Localized versions of LinkedIn's auto-generated `#hiring` template: the first capture
  found none (its 10 `ats_echo` rows are all English). A later probe found German
  (one row), French (one) and Portuguese (one, pt-PT); the fixture holds those four
  and the tests treat them as real. Spanish was probed and no fixed template was
  confirmed -- the near hits read as ordinary human copy -- so the parser claims none.
  The French and Portuguese posts carry a localized slug, which the parser's bare-`hiring`
  slug rule does not cover; they are recognized by their closing sentence.
- A `-share-` url: one was seen in a review capture and is not in this fixture. It is
  handled like `ugcPost` (a real post, declined as `unsupported_urn`); tests for it
  use a synthetic url.
- Engagement counts other than the English `N comments` title segment (a
  Portuguese title shows a truncated `| 20 ...`, so localized counts exist but are
  unreadable here). Localized and abbreviated counts (`20 comentarios`, `1.2K
  comments`) are covered by synthetic tests only.
- Titles in the form `<Name> on LinkedIn: <content>`; a targeted query found none
  from this provider.
- Results from providers other than Firecrawl (Brave, You.com, Serper). Their title
  and stamp shapes may differ; the P3 phase should extend this fixture from a real
  pull with each.
